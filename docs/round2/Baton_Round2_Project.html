Baton: a handover that writes only what it can cite

Baton turns a project's notes, chat, task board, commits and GitHub issues into a handover where every line carries an exact source quote checked by code, every gap is labelled, a human reviewer approves before anything is shared, and each reader receives only the rows Postgres row-level security lets them see.

1. Try it in two minutes

  1. Open the link and click Try the Meridian sample. Six synthetic sources load (meeting notes, chat export, task CSV, GitHub comments, commit log, a treasurer-only note).
  2. Follow the Next step bar. Reconstruct extracts 26 claims with exact quotes, masks 3 planted secrets and quarantines one planted "ignore previous instructions" message.
  3. Verify shows every claim's checks. In the Quote guard lab, change "100" to "200" or add "not" and watch the claim get rejected. Run tests and Run database probes show the leak tests live.
  4. Review: decide claims, resolve the deploy-owner conflict, answer gaps, view the handover as each reader. Or press Fast-forward the demo review: it makes the standard decisions (logged, changeable) and stops at the gate. Approving and publishing is always a human click.
  5. Handover: switch between Meera, Rohan and Kavya. Each receives a different plan from the same approved version, served by Postgres row-level security; a hidden item looks exactly like a missing one.

2. The problem, briefly

When someone leaves a project, the reasons behind decisions, work in flight, dependencies and contacts leave with them. That knowledge sits in chats, pull requests, meeting notes and task boards. Studies of open-source turnover show the risk is real: Avelino et al. found 315 of 1,932 popular projects lost all their truck-factor developers; Nourry et al. found 32,689 of 36,464 projects lost all core developers at least once. A generic AI summary is fluent but can invent details, hide uncertainty and repeat confidential text to the wrong reader. Baton's rule: the system may write only what it can cite; everything else is shown as a labelled gap.

How permissions are enforced (twice)

1. In Postgres. Policies read the request's workspace and persona. Staff personas may write the ledger; readers may only select their own handover rows: baton_can_read(access) and not withheld and version approved. Readers get zero rows from sources and claims, and nothing at all without a workspace id.
2. In composition. Each reader's handover is built only from the rows that reader may see; conflicts, superseded labels and gaps are computed per reader; the gap row is identical whether an item is missing or hidden. The app compares the database's answer with its own permission check and shows whether they match.

7. Three major improvements for Round 3

1. Real identities and permission hardening, enforced end to end

Replace demo personas with Supabase Auth so RLS trusts a signed JWT instead of a header; a data-owner approval flow for access requests that actually grants a tag for one item; server-side logging of who viewed what; and the canary, differential, injection and database-probe suites running in GitHub Actions against a fresh database on every push. Why it matters: it turns "readers only see their rows" from a demo property into a production one.

2. Model-assisted extraction and a guided gap interview

A server-side function (FastAPI or a Supabase Edge Function) calls Claude through a provider interface with responses cached per reader, proposes richer claims from messy sources, and makes the separate support-check call. The same code verifier still decides what may be stored. The manual gap answers become a guided interview with ranked, targeted questions for the departing person (aim: 15 to 20 minutes). Why it matters: real-world sources are messier than rules can cover, while the trust guarantee stays in code.

3. Handover quality report and an honest benchmark

A scored coverage view (share Sourced, open gaps, unresolved conflicts, single-owner risks), evaluated against the seeded Meridian benchmark (about 40 planted facts, 5 only in the leaver's answers) and a held-out set in different export formats written by a teammate who did not build the importers; recall, support-check precision and fabrication rate reported, including misses; plus the teammate pilot timing raw sources vs a plain LLM summary vs Baton. Why it matters: it measures whether Baton is right, not just whether it runs.
