Baton: a handover that writes only what it can cite

When someone leaves a project, Baton rebuilds what they knew from notes, chats, task boards and pull requests as a ledger of small claims. Every claim carries an exact source quote checked by code and again by the database. AI proposes more claims and audits the evidence, but never decides what is shared: a reviewer does. Each reader signs in and receives only the rows Postgres row-level security allows.

3. Other improvements after Round 2

  • Reader experience: each reader has their own page served only from Postgres with their token; acknowledgements and access requests are stored per account.
  • Reliability: source validation (empty, oversized over 150 k characters, duplicate, unreadable JSON or CSV, nothing readable after parsing); publishing can't run twice at once; AI and benchmark runs survive a page reload; a fast account switch can no longer show the previous account's page or results (a routing bug found in testing and fixed); every database or AI failure falls back to the rule-based results with a visible reason.
  • Security: the security advisor is clean (helper functions run with the caller's rights); secret masking now also catches "password was …", PIN and passcode forms.
  • Importers: Slack exports (user_profile.real_name, epoch timestamps) and Jira-style CSV headers.
  • Documentation: a README someone else can clone and run from, with the Supabase setup, AI configuration and tests.

5. Technical architecture and implementation

Identity and permissions

Supabase Auth issues a JWT; PostgREST verifies it; RLS helper functions read auth.uid() and the user's workspace membership. The x-baton-workspace header only selects a workspace and is honoured only for members. Readers can never read sources, the claim ledger, the audit log or interview answers; they read published rows through a security_invoker view filtered by their access tags.

Trust checks on the server

baton_check_claim: an extracted or Sourced claim must quote its stored source (exact or trigram match ≥ 0.8 with numbers guarded). baton_check_version: reviewer only, no undecided claims or open disputes; the server sets approver and time. baton_check_item: a published row must equal an approved claim. Versions are immutable except retraction.

AI pipeline

Browser → /api/ai with the user's token → token and staff role verified with Supabase → passages cleaned (no links, HTML or instruction-like text) → one chunk per call, JSON-schema output → every proposal through engine.js verifyClaim → separate evidence-check call → contradiction audit. Model: GPT-OSS-120B (open weights) on the Vercel AI Gateway free credit, with GPT-5-mini and Mistral Small as fallbacks; Claude through the Anthropic API when a key is set (provider interface). Cache: ai_cache keyed by model, task and input.

Stack

Static single-page app (HTML, CSS, JavaScript, GSAP, Lenis), Vercel (site and function), Supabase (Postgres, RLS, Auth), Node test runner, GitHub Actions with the Supabase CLI. Six migrations: schema and RLS, advisor fix, auth and server checks, helper rights, AI cache, guided interview. The same engine.js runs in the browser, the server function and the tests.

8. Product roadmap and future development

NEXT 4 WEEKS

Real teams

  • Invite by email; roles per workspace chosen by the owner
  • Slack and GitHub OAuth connectors that sync, not upload
  • PDF and Google Docs import
  • Teammate-written held-out benchmark
NEXT 3 MONTHS

Better knowledge

  • Continuous handovers: update the ledger weekly, so leaving is a non-event
  • Owner approval flow that grants one tag for one item
  • Per-claim history and diffs between versions
  • Evaluation dashboard tracking recall and fabrication over time
LATER

Scale and trust

  • Server-side extraction jobs with queues
  • Organisation-wide policies (retention, sensitive tags)
  • SSO for universities and companies
  • On-premise model option for confidential projects

Who it is for: student project teams and clubs (the Meridian scenario), research labs where students rotate every semester, and small engineering teams where one departure takes undocumented knowledge with it. The design principle stays the same at every stage: AI may propose, code must verify, a person decides, and the database enforces who sees what.
