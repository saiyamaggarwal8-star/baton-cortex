01 · PRODUCT OVERVIEW & CORE RULE

Product: Baton, a verifiable knowledge-handover tool
Team: Cortex (Bennett University)
Stage: Final round (Round 3). This page describes the product as built and live. Anything not built is marked Planned.

The problem

When someone leaves a project (graduating club lead, intern at term end, volunteer stepping down), the reasoning behind decisions, unfinished work, dependencies and contacts leaves with them. That knowledge is scattered across chats, pull requests, meeting notes and task boards. The new person reads months of threads or guesses.

The solution

Baton rebuilds a project's current state from authorised sources as a ledger of small, checkable claims. Each claim has a source quote, a label and an access tag. The handover is built only from approved claims. Anything the system cannot prove is shown as a labelled gap, never as a guess. Each reader sees only the claims they are allowed to see.

Three differentiators

  • Evidence before prose: a claim is labelled Sourced only if code finds its quote in the source, the exact-token guard passes and the support check agrees.
  • Gap interview: ranked questions about only what the sources cannot answer, sent to the departing lead's own account.
  • Permission-first generation: each reader's handover is built only from claims that reader may see, enforced by Postgres row-level security.

The core rule

“The system may write only what it can cite. Everything else is shown as a labelled gap.”
  • A claim whose quote cannot be found is never stored: refused by the code verifier, and again by Postgres on save.
  • The handover text is rendered by code from approved claim statements. No model writes reader-facing text.
  • Nothing reaches a reader before the reviewer publishes; the database enforces this.

02 · END-TO-END WORKFLOW (5 STEPS)

1. CONNECT 2. RECONSTRUCT 3. VERIFY 4. REVIEW (HUMAN GATE) 5. HANDOVER

Step 1: Connect · Data owner (Priya)

  • Paste or upload Markdown, text, CSV and JSON. Chat exports, including Slack JSON. Task-board CSVs with any headers (column mapping, e.g. Jira).
  • Import a public GitHub repository (README plus 20 issues and pull requests) through the GitHub REST API.
  • Choose an access tag for each source (all_members, core_team, treasurer_only).
  • Secrets and personal data are masked on import, before text is stored or sent to the model.
  • Empty, oversized, duplicate and unreadable sources are refused with a reason.

Step 2: Reconstruct · System

  • Split sources into passages that keep source, author and date.
  • Rule extractors propose typed claims, each with its exact source sentence.
  • Optional AI extraction (server function, GPT-OSS-120B) adds decisions with rationale, tasks with owners and deadlines, dependencies, risks, open questions and contacts. Each proposal must quote its source.
  • Instruction-like text is quarantined: it never becomes a claim and is never sent to the model.
  • Ownership is inferred from commit counts (labelled Inferred, with the numbers shown).

Step 3: Verify · Plain code, then the database

  • Match each quote against its passage: exact first, fuzzy sliding-window fallback, exact-token guard for numbers, versions, paths, identifiers and negations.
  • Rules support check, then a separate AI evidence check. Doubtful claims are held for a person.
  • Failed claims are never stored. Postgres re-checks every extracted quote against the stored source on save.
  • Conflicts, gaps and stale-fact hazards are computed per reader.

Step 4: Review · Human gate (Reviewer Prof. Rao, departing lead Aarav)

  • The reviewer accepts, edits or rejects each claim. A random sample (10%, at least 5) comes before bulk approval, which covers low-risk claims only.
  • View as each reader; the reviewer confirms each view, and confirmations reset after any change.
  • Guided interview: ranked questions go to Aarav's account; his answers return as Stated by Aarav claims that the reviewer still decides on.
  • The publish gate lists 8 checks. The database refuses to publish unless the caller is the reviewer, with no undecided claims and no open disputes.

Step 5: Handover · Each reader

  • A continuation plan built only from approved claims that reader may see: ownership, first-week actions, risks, decisions and a timeline.
  • Gap rows look identical whether an item is missing or hidden; Request access sits on each one.
  • The reader acknowledges each item; receipts are stored per account.
  • Every approved version is immutable, has a content hash and can be retracted.

05 · PERMISSIONS, PRIVACY & ZERO EXISTENCE LEAKAGE

Permission principles

  • Each source has an access tag. Each extracted claim has exactly one source and inherits that source's tag.
  • Claims with no single source (leaver answers, reviewer edits) carry an explicit tag chosen by a person.
  • Permissions are enforced twice: PostgreSQL row-level security on every table, and composing each handover only from claims the reader may see.

How the database enforces it

  • Supabase Auth issues a JWT; RLS reads the user from it (auth.uid()). The anonymous key alone reads nothing.
  • Roles are per workspace. The x-baton-workspace header only selects a workspace; it is honoured only for its members.
  • Workspaces are isolated by team. A new workspace adds its owner and the owner's own demo team, nobody else. The probes create two workspaces in different teams and check that neither side can read or write the other.
  • Readers read published rows through a security_invoker view filtered by their access tags; they cannot read sources, the ledger or the audit log.
  • Triggers refuse misquoted claims, publishing by anyone but the reviewer, publishing with undecided claims or open disputes, published rows that differ from approved claims, and edits to approved versions.

Zero existence leakage

Where a reader's view has no answer, Baton shows exactly:

“No answer found in your view. It may be undocumented or restricted”

with a Request access button. The row is identical whether the item is missing or hidden. No counts, no stubs like "2 items need access", no existence signals.

AI containment

  • The browser never talks to a model. The server function verifies the caller's token and staff role; readers never trigger model calls.
  • The model has no tools and sees one source chunk per call, with one access tag. Links and HTML are stripped, and quarantined passages are never sent.
  • Every proposal is re-checked by the same code verifier; responses are cached in a staff-only Postgres table.

07 · DATABASE SCHEMA (14 TABLES + 1 VIEW) & API

Tables (Supabase Postgres, RLS on every table, 7 migrations)

profiles personas workspaces workspace_members sources claims versions handover_items receipts access_requests audit_log interview_questions interview_answers ai_cache reader_handover (view)

API

There is no custom backend server for data. The browser talks to Supabase's REST API (PostgREST) with the signed-in user's JWT, so every read and write passes through RLS and the triggers. AI work goes through one Vercel Function:

CALLWHOPURPOSE
GET /api/aiAnyoneStatus: provider, active model, fallback list
POST /api/ai · extractStaffAI claim proposals, code-verified, then evidence-checked
POST /api/ai · supportStaffDoes this quote support this statement?
POST /api/ai · conflictsStaffContradictions and outdated decisions across claims
POST /api/ai · interviewStaffTailor the ranked gap questions
POST /api/ai · probeModelsStaffWhich gateway models this account may call

Triggers (server-side trust checks)

  • baton_check_claim: the quote must be in the stored source; numbers guarded.
  • baton_check_version: reviewer only; no undecided claims or open disputes; the server sets the approver and time.
  • baton_check_item: each published row must equal an approved claim.
  • baton_check_version_update: approved versions are immutable except retraction.
  • baton_on_workspace_created: adds the owner and the owner's own demo team only.

Definition of done

  • [✓] A judge opens the hosted link, signs in with a demo account and imports a source.
  • [✓] Sources produce labelled, cited claims; failed claims are not stored.
  • [✓] The reviewer can accept, edit, reject, resolve conflicts and view as each reader.
  • [✓] Publishing is blocked until the gate passes, and the database enforces it.
  • [✓] An approved handover reaches each reader, who acknowledges it item by item.
  • [✓] Hidden and missing items look identical to the reader.
  • [✓] Canary, differential, injection and database tests pass.

11 · LIMITATIONS, ROADMAP & HONEST WORDING

Known limitations

  • Demo data is synthetic and the demo accounts are public; they protect synthetic data only.
  • Masking is heuristic: we report "zero canaries across the readers tested", never "no secrets leak".
  • The benchmark sets are small and team-written.

Planned (not built)

  • Next 4 weeks: email invitations with owner-chosen roles; Slack and GitHub OAuth connectors that sync; PDF and Google Docs import; a teammate-written held-out benchmark.
  • Next 3 months: continuous handovers updated weekly; an owner approval flow that grants one tag for one item; per-claim history and version diffs; an evaluation dashboard.
  • Later: server-side extraction jobs; organisation-wide policies; SSO; an on-premise model option.

Non-goals

Question-answering chatbots, publishing without approval, real confidential data in the demo, scoring or ranking individuals.

Honest wording

  • We say "we found no tool that documents claim-level quote verification, a gap-targeted leaver interview, permission-first generation and per-claim approval together", never "first", "only" or "nobody does this".
  • We do not promise reduced ramp-up time or fewer incidents; we have not measured them.
