01 · PRODUCT OVERVIEW & CORE RULE

Product: Baton, a verifiable knowledge-handover tool
Team: Cortex (Bennett University)
Stage: Build window (Rounds 2 and 3); Round 1 was planning only.
Audience of this file: an AI coding agent (Antigravity) and the four team members building the product.

The problem (PRD Section 1.1)

When someone leaves a project (graduating club lead, intern at term end, volunteer stepping down), the reasoning behind decisions, unfinished work, dependencies and contacts leaves with them. That knowledge is scattered across chats, pull requests, meeting notes and task boards. The new person reads months of threads or guesses.

The solution (PRD Section 1.2)

Baton rebuilds a project's current state from authorised sources as a ledger of small, checkable claims. Each claim has a source quote, a confidence label and a permission tag. The handover is written only from claims. Anything the system cannot prove is shown as a labelled gap, never as a guess. Each reader sees only the claims they are allowed to see.

Three differentiators (PRD Section 1.3)

  • Evidence before prose: A claim is labelled Sourced only if its quote is found in the source by code and a separate check agrees the quote supports the statement.
  • Gap interview: Ask the departing person only what the sources cannot answer (target 15 to 20 minutes).
  • Permission-first generation: Each reader's handover is built only from claims that reader may see.

The Core Rule (must always hold, PRD Section 2)

“The system may write only what it can cite. Everything else is shown as a labelled gap.”
  • A claim whose quote cannot be found, or whose support check says no, is never stored.
  • The handover composer sees claim IDs and statements only, never raw sources.
  • A sentence in a handover with no claim citation is rejected by a code check.
  • Nothing reaches the incoming person before an approver signs off.

02 · END-TO-END WORKFLOW (5 STEPS)

1. CONNECT 2. RECONSTRUCT 3. VERIFY 4. REVIEW (HUMAN GATE) 5. HANDOVER

Step 1 — Connect · Data owner

  • Link a GitHub repo (issues, PRs, comments, commits, README) via the GitHub REST API.
  • Upload meeting notes (Markdown, text, PDF), a chat export (JSON or text) and a task board (CSV).
  • CSV column-mapping screen so unfamiliar headers can be mapped before import.
  • For each source choose an access tag (for example all_members, core_team, treasurer_only).
  • Secrets and personal data are masked on import, before text is stored for display or sent to any model.

Step 2 — Reconstruct · System

  • Split sources into passages that keep source, position and author.
  • Ask the LLM to propose typed claims, each with an exact source quote and location.
  • Build a timeline of decisions, changes and open discussions.
  • Infer who works on which area from commit and review activity (labelled Inferred, with the numbers shown).

Step 3 — Verify · System, plain code

  • Match each quote against the source passage (exact first, fuzzy fallback, exact-token guard).
  • Run the support check (does the quote support the statement?).
  • Assign labels. Failed claims are never stored.
  • Run slot-based conflict detection and checklist-based gap detection, computed per reader.

Step 4 — Review · Human gate (Reviewer + Leaver)

  • Reviewer accepts, edits or rejects each claim and resolves conflicts.
  • Reviewer uses View as to see each reader role's real view and must confirm they read it for each role.
  • Leaver answers gap questions (typed answers become Confirmed by or Stated by claims).
  • Every change is versioned. Document stays marked Draft until approval.
  • Rejecting or correcting sends the ledger back to Reconstruct.

Step 5 — Handover · Incoming member

  • Build a continuation plan only from claims that reader may see: ownership-transfer table, first-week action list (ordered), open risks and blockers, timeline.
  • The incoming person acknowledges each item (receipt).
  • Every approved version is stored and immutable (can be retracted).

9 Claim types (PRD Section 7.1)

Claim fields

Verification Labels & Strict Meaning (PRD Section 7.3 & Section 19)

Critical Rule: Do NOT use the word "Verified" in the UI. Use only the exact labels below.

LABELMEANINGWHAT IT DOES NOT PROVE
SourcedQuote found in source (exact or fuzzy), exact-token guard passed, and support check agrees quote supports statement.That statement is true or still current.
Quote-onlyQuote found and guarded, but support check was unavailable or over budget.Everything Sourced does not prove, plus that quote supports statement.
InferredSupport check says "partly", or derived from a pattern (e.g. commit counts), shown with numbers behind it.Anything beyond the numbers shown.

Confirmed by [person], [date]Leaver confirms an extracted claim shown to them.Truth beyond that person's word.
Possible conflict / SupersededComputed per reader: same subject and slot, different values. Stays side by side until human resolution.Which side is right. Never a verdict.
MissingA handover-checklist item has no claim in the reader's view.That nothing exists (may be undocumented or restricted).

05 · PERMISSIONS, PRIVACY & ZERO EXISTENCE LEAKAGE

Permission Principles (PRD Section 9.1)

  • Each source has an access tag. Each extracted claim has exactly one source and inherits that source's access list.
  • Claims with no single source (leaver answers, reviewer edits, derived claims) carry an explicit access list never wider than the claims they rest on.
  • A claim built on several sources takes the strictest access tag among them unless split by the reviewer.
  • Permissions are enforced twice: (1) PostgreSQL Row-Level Security (RLS), (2) composing each handover only from claims the reader may see.

Zero Existence Leakage Rule (PRD Section 9.2)

Where a reader's view has no answer, show exactly:

“No answer found in your view. It may be undocumented or restricted”

accompanied by a Request access button. The row must be identical whether the item is missing or hidden. No counts, no stubs like "2 items need access", no existence signals.

Generation Safety & Prompt Containment

  • Retrieval and composition run per reader and per request, after database filtering.
  • Text the reader may not see is never placed in the prompt.
  • Nothing is cached across readers.
  • The composer sees only permitted claim IDs and statements, never raw sources.
  • Default handover is rendered by code from claim statements. Any model-written sentence must cite one claim ID; uncited sentences are rejected.

Definition of Done (PRD Section 20)

  • [✓] A judge opens the hosted link and imports a source.
  • [✓] Sources produce labelled, cited claims; failed claims are not stored.
  • [✓] Reviewer can accept, edit, reject, resolve conflicts, and view as each role.
  • [✓] Publishing is blocked until hazard checks and per-role view confirmations pass.
  • [✓] One approved handover reaches the incoming person; they acknowledge item by item.
  • [✓] Hidden and missing items look identical to the reader.
  • [✓] Canary, differential and injection tests pass in CI.
  • [✓] Quote-checker mutation test shows zero false accepts on digits, identifiers and negations.

11 · NON-GOALS, HONEST WORDING RULES & FUTURE SCOPE

Non-goals (PRD Section 3.2)

Live Slack/Teams OAuth, real-time sync, SSO/SCIM, question-answering chatbots, unapproved publishing, real confidential data, scoring/ranking individuals.

Honest Claims & Wording Rules (PRD Section 19)

  • Say "we found no tool that documents claim-level quote verification, a gap-targeted leaver interview, permission-first generation and per-claim approval together." Never say "first", "only" or "nobody does this".
  • Do NOT promise reduced ramp-up time or fewer incidents. No study measures this.
  • Turnover evidence: use exact numbers from Avelino et al. (1,932 projects, 315 lost truck-factor, 128 survived) and Nourry et al. (36,464 projects, 32,689 affected, 27.07% recovered).
  • Do NOT use the word "Verified" in the UI. Use labels: Sourced, Inferred, Stated by, Confirmed by, Possible conflict, Missing.
